# Mercury KM09-810H (MediaTek MT7622) — Custom U-Boot Bootloader

Complete, reproducible bootloader project for the **Mercury KM09-810H** router
(MediaTek MT7622, SPI-NAND Macronix MX35LF1GE4AB 128 MiB). Everything needed —
source, config, device tree, build script, build outputs and the stock
bootloader backup images — lives in this repository and is synced to GitHub.

## Repository layout

| Path | Purpose |
|---|---|
| `configs/mt7622_mercury_km09_810h_defconfig` | U-Boot configuration (MTD stack, GMAC1+MT7530, failsafe bootmenu/httpd) |
| `arch/arm/dts/mt7622-mercury-km09-810h.dts` | Board device tree (GMAC1, `mediatek,cpu-port = <5>`, SPI-NAND, GPIO reset) |
| `drivers/net/mtk_eth/mt7530.c` | MT7530 switch driver, extended with Port5-CPU support |
| `board/mediatek/mt7622/km09-810h-build.sh` | One-command build (U-Boot + TF-A BL2/FIP, all variants) |
| `arm-trusted-firmware/` | TF-A (mtksoc branch) as a **git submodule** |
| `output/km09-810h/` | Pre-built flashable artifacts (regenerated by the script, committed) |
| `output/km09-810h/stock/` | Stock Preloader/ATF/Bootloader/Config/Factory partitions extracted from the NAND dump (for full recovery) |
| `/home/baalwy/km09-810h/extracted/` | Full stock NAND dump incl. large partitions (Image1/2, Rootdata, Userdata) — kept outside the repo |

Fresh clone:

```sh
git clone --recurse-submodules https://github.com/baalwy/mtk-u-boot.git
# or after a plain clone:
git submodule update --init
./board/mediatek/mt7622/km09-810h-build.sh all
```

## Verified hardware facts

* Boot chain: BootROM → **BL2** (TF-A, NFI+BRLYT) → **BL31** (ATF) → **BL33**
  (U-Boot), packaged as a FIP loaded from logical offset `0x80000`.
* LAN: external **MT7530** switch @ MDIO `0x1f`, CPU link on **switch Port5
  (GMAC5/RGMII) ↔ MT7622 GMAC1**. LAN1–4 = MT7530 PHY ports 4,3,2,1
  (vendor DTB `switch@1f port@5 label "cpu"`, stock strings
  `GMAC1 Force link status enable !!` / `MT7530 Reset Completed!!`).
  The mtksoc `mt7530.c` defaults to Port6 as CPU → the board DTS sets
  **`mediatek,cpu-port = <5>`**.
* WAN: GMAC0 behind an Aquantia 2500base-x PHY (unused by U-Boot).
* Bad-block management: stock MediaTek **BMT v2** — do NOT enable NMBM/UBI.
* DDR: 512 MiB; 1-chip vs 2-chip topology not confirmed → both `1ddr`
  (`DDR3_FLYBY=0`) and `2ddr` (`DDR3_FLYBY=1`) images are built. Use
  whichever boots in the RAM/UART test.

## Driver fixes in this fork

- **MT7530 PHY auto-negotiation (`drivers/net/mtk_eth/mt7530.c`)**: the internal
  LAN PHYs come out of reset with `BMCR == 0x0000`, i.e. auto-negotiation
  DISABLED (measured live via `mdio read ethernet@1b100000 <0-4> 0x0`). The
  stock Linux PHY stack hides this by running `genphy_restart_aneg()` when the
  interface is brought up; U-Boot never did, so `mt7530_setup()` only cleared
  `BMCR_PDOWN` and wrote the (zero) value back. Lenient link partners (home
  switches, some Realtek NICs) still connect via parallel detection, but strict
  ones (e.g. Intel Gigabit ET server NICs) refuse an AN-disabled partner and
  the port just flaps (`link established / disconnected` every ~25s in the
  Windows event log). Fix: after powering the PHYs, `mt7530_setup()` now writes
  `BMCR = BMCR_ANENABLE | BMCR_ANRESTART` (0x1200) and advertises 1000BASE-T FD+HD
  via `MII_CTRL1000 = 0x0300` for every LAN port.
  **Verified live (Oct 20 2026):** after reflash, `BMCR` reads `0x1000` (AN on,
  restart bit self-cleared) and `ping 192.168.1.2` → `host is alive` against the
  previously-refusing Intel Gigabit ET server NIC. Note: MT7530 BMSR link bit is
  latch-on-read; trust `ping` over a single BMSR sample.
- **`cmd/mdio.c` crash** on addresses with a bound `phy_device` (e.g. MT7530 mgmt
  PHY 31): plain accesses now always use the raw bus read/write path.
- **`net/net.c` TCP dispatch (httpd dead port 80)**: incoming TCP reached
  `mtk_receive_tcp()` only under `#if defined(CONFIG_PROT_TCP)`, which our
  config leaves off — so `httpd` accepted SYN packets into the void (ping/TFTP
  fine, browser hung, nmap showed all ports filtered). Added an
  `#elif defined(CONFIG_MTK_TCP)` path so the MTK TCP framework gets packets
  regardless of upstream PROT_TCP.
- **`cmd/mtd.c`** bad-block hang + data-shift fixes (see restore section below).

## Stock flash layout (logical offsets)

| Region (stock names) | Offset | Size | U-Boot mtdparts name |
|---|---|---|---|
| Preloader (BL2) | `0x000000` | 512 KiB | `bl2` |
| ATF | `0x080000` | 256 KiB | `fip` (unified 768 KiB) |
| Bootloader (LK U-Boot) | `0x0C0000` | 512 KiB | `fip` (unified 768 KiB) |
| Config | `0x140000` | 512 KiB | `Config` |
| Factory (MAC/RF cal!) | `0x1C0000` | 256 KiB | `Factory` |
| Image1 | `0x200000` | 48 MiB | `firmware` (boot slot; was `Image1`) |
| Image2 | `0x3200000` | 48 MiB | `Image2` |
| Rootdata | `0x6200000` | 16 MiB | `Rootdata` |
| Userdata | `0x7200000` | 14 MiB | `Userdata` |

`Config`/`Factory` hold calibration and configuration data — **never erase or
write them unless restoring from your own backup**.

The boot slot at `0x200000` MUST be labeled `firmware` in `CONFIG_MTDPARTS_DEFAULT`:
the vendor failsafe code (`mtd_upgrade_image()`/`mtd_boot_image()` in
`board/mediatek/common/mtd_helper.c`) looks the partition up by that literal
name (hardcoded in `dual_boot.h`). With any other name, web-UI firmware uploads
fail with "Image not supported!" (nothing written) and bootmenu option 1
(`mtkboardboot`) returns -ENODEV. The failsafe upload accepts OpenWrt/Mercury
update images (TRX/OWRT parsed by `verify_image_ram()`), NOT raw partition
binaries or the 128MiB dump — those go in via `tftpboot` + `mtd write`.

## Build

```sh
./board/mediatek/mt7622/km09-810h-build.sh uboot   # U-Boot only (in-tree)
./board/mediatek/mt7622/km09-810h-build.sh ram     # TF-A RAM/UART bl2+fip (1ddr+2ddr)
./board/mediatek/mt7622/km09-810h-build.sh snand   # TF-A SPI-NAND bl2.img+fip (1ddr+2ddr)
./board/mediatek/mt7622/km09-810h-build.sh all     # everything
```

Outputs land in `output/km09-810h/` with a SHA-256 log in
`manifest-build.txt`. Every artifact is written twice: once with a fixed
name (used by the examples below) and once with the build date/time baked
into the filename, `name-YYYYmmdd-HHMMSS.ext` (local time), so a flashed file is
self-identifying. Only the current timestamped set is kept; older ones are
removed on the next build. Important files:

* `bl2-ram-uart-<variant>.bin` + `fip-ram-uart-<variant>.bin` — RAM/UART test
* `bl2-snand-2k64-<variant>.img` — flashable BL2 (**use the `.img`, never
  `.bin`: it carries the BootROM NFI header**)
* `fip-snand-<variant>.bin` — BL31+BL33 package for the `fip` region
* `u-boot-km09-810h.bin` / `.dtb` — raw U-Boot (BL33) and board DTB

## Step 1 — RAM/UART test (non-destructive)

Nothing is written to NAND; power-cycling restores stock behavior.

```sh
mtk_uartboot -s /dev/ttyUSB0 \
    -p output/km09-810h/bl2-ram-uart-1ddr.bin \
    -f output/km09-810h/fip-ram-uart-1ddr.bin
```

Power-cycle the router exactly when `Handshake...` appears. If DRAM training
fails, repeat with the `2ddr` pair. In the console verify:

```
KM09-810H> printenv          # mtdparts must show bl2/fip
KM09-810H> nand list         # MX35LF1GE4AB + partition table
KM09-810H> ping 192.168.1.2  # cable on a LAN port, PC static 192.168.1.2/24
```

## Step 2 — Write to NAND (production)

From a working U-Boot (RAM test or the stock bootmenu's TFTP entries):

```
tftpboot 0x46000000 bl2-snand-2k64-1ddr.img
mtkupgrade bl2
# fallback: mtd erase bl2 && mtd write bl2 0x46000000 0 $filesize

tftpboot 0x46000000 fip-snand-1ddr.bin
mtkupgrade fip
# fallback: mtd erase fip && mtd write fip 0x46000000 0 $filesize
```

`mtkupgrade` validates the BRLYT/FIP headers before writing
(`CONFIG_MTK_UPGRADE_BL2_VERIFY/_FIP_VERIFY`).

### Offline reflash via `loady` (no network needed)
When TFTP is unavailable, pull images into RAM over UART with Ymodem
(TeraTerm: File → Transfer → Ymodem → Send) and flash with `mtkupgrade`
(it uses `fileaddr`/`fileSize` set by `loady`):

```
loady 0x46000000         # send bl2-snand-2k64-1ddr.img
mtkupgrade bl2
loady 0x46000000         # send fip-snand-1ddr.bin
mtkupgrade fip
reset
```

### Chain-consistency rule (NEVER mix stock and custom small partitions)
The stock and custom boot chains interpret the same NAND offsets differently:

| Offset | Stock chain | Custom chain |
|---|---|---|
| 0x000000 | `Preloader.bin` (2018 PL FM) | `bl2` = bl2-snand-2k64-1ddr.img |
| 0x080000 | `tee1` = `ATF.bin` (MTK part header) | start of `fip` (TF-A FIP magic) |
| 0x0C0000 | `lk` = `Bootloader.bin` (stock U-Boot) | inside our `fip` |

Mixing them bricks NAND boot: with the stock Preloader in `bl2` and our FIP in
`fip`, the PL cannot parse a tee1 header at 0x80000 → `load tee1 (ret=-1)` →
`PL fatal error...` (WDT loop). Recovery = restore the consistent triple from
`~/km09-810h/extracted/` (Preloader.bin→bl2, ATF.bin→tee1 area, Bootloader.bin→lk)
via loady, or reflash OUR pair together (bl2-snand img + fip-snand bin).
Always flash both ends of a chain in the same session.

### Whole-chip logical dump restores DATA, not Mercury `mcr` state
Verified on HW (Oct 20 2026): `tftpboot` + `mtd erase spi-nand0` + `mtd write
spi-nand0 0x46000000 0 0x8000000` of the logical 128MiB dump completes without
hangs (bad block 0x76a0000/BBT-0x3b5 handled, kernel FIT hashes verify on BOTH
Image1 @0x200000 and Image2 @0x3200000) — but the stock LK then boot-loops:
`MCR Image Checksum Error` → rewrites the mcr control region @0x180000 → reset →
flips BOOT SIDE 1↔2 forever, never reaching Linux. Cause: `mcr` is Mercury's
A/B boot-confirmation state kept with vendor-specific OOB/ECC semantics that a
data-only dump cannot round-trip. Remedies: (a) boot our custom chain instead,
(b) reflash the official Mercury firmware image (`mtkupgrade fw` / web failsafe),
which regenerates mcr correctly. The dump remains valid as a content backup and
for custom-chain reflash.


## Failsafe / recovery features (built in)

* Press any key during boot → **bootmenu** (`mtkload`, `mtkupgrade bl2/fip`,
  `Start Web failsafe`, …).
* `httpd` → web failsafe UI at `http://192.168.1.1/` (upload a combined
  firmware image; Ctrl+C quits).
* With boot failure the web failsafe starts automatically
  (`CONFIG_MTK_WEB_FAILSAFE_AFTER_BOOT_FAILURE=y`), like the stock behavior.

## Restoring the STOCK firmware from the NAND dump

Backup files: small partitions are committed in `output/km09-810h/stock/`,
the large ones stay in `/home/baalwy/km09-810h/extracted/`
(sha256 list in its `manifest.txt`). Serve one of these directories over TFTP
from the PC (192.168.1.2), e.g.:

```sh
# PC side (any tftp server works; dnsmasq example, serving both dirs):
sudo dnsmasq --port=0 --enable-tftp \
  --tftp-root=/home/baalwy/km09-810h/extracted --tftp-root=/path/to/stock
```

U-Boot syntax used below:
`mtd write <name> <addr> [<off> [<size>]]` — note the order: the **3rd
argument is the offset** (relative to the partition start), the 4th is the
size; omitting the size writes the entire partition. Always `mtd erase` the
partition first.

> **Use literal hex sizes, never `$filesize`.** Pass the exact hex value from
> `tftpboot`'s `Bytes transferred = NNNN (HEX hex)` line (as below). Writing
> `... 0 $filesize` on a `;`-separated compound line
> (`tftpboot ...; mtd write ... $filesize`) silently writes **0 bytes**: this
> build expands `$filesize` at line-parse time — before the same-line
> `tftpboot` runs — so it is still empty and `hextoul()` returns 0. The
> partition gets erased then left blank; wiping `bl2` this way halts the next
> boot in the SoC ROM (`System halt!`). If you insist on `$filesize`, run
> `tftpboot` alone on one line, press Enter, then `mtd write` on the next line.
>
> Also erase a partition **once**, before writing it. For the merged `fip`
> (stock `tee1`=ATF + `lk`=Bootloader): `mtd erase fip` a single time, write
> ATF at offset `0` and Bootloader at offset `0x40000` — a second `mtd erase
> fip` before the Bootloader write re-wipes the ATF (`load tee1 (ret=-1)` →
> `PL fatal error`).

```
# ---- bootloader area (bl2 = stock Preloader, fip = ATF + Bootloader) ----
tftpboot 0x46000000 Preloader.bin
mtd erase bl2
mtd write bl2 0x46000000 0 0x80000

tftpboot 0x46000000 ATF.bin
mtd erase fip
mtd write fip 0x46000000 0 0x40000

tftpboot 0x46000000 Bootloader.bin
mtd write fip 0x46000000 0x40000 0x80000

# ---- configuration & calibration ----
tftpboot 0x46000000 Config.bin
mtd erase Config
mtd write Config 0x46000000 0 0x80000

tftpboot 0x46000000 Factory.bin
mtd erase Factory
mtd write Factory 0x46000000 0 0x40000

# ---- system partitions ----
tftpboot 0x46000000 Image1.bin
mtd erase firmware
mtd write firmware 0x46000000 0 0x3000000

tftpboot 0x46000000 Image2.bin
mtd erase Image2
mtd write Image2 0x46000000 0 0x3000000

tftpboot 0x46000000 Rootdata.bin
mtd erase Rootdata
mtd write Rootdata 0x46000000 0 0x1000000

tftpboot 0x46000000 Userdata.bin
mtd erase Userdata
mtd write Userdata 0x46000000 0 0xE00000

reset
```

One-shot whole-chip alternative (erases everything, then writes
`logical-128MiB.bin` from `0x46000000`; slow, and bad-block remapping will
differ from the stock BMT state — prefer the per-partition procedure):

```
tftpboot 0x46000000 logical-128MiB.bin
mtd erase spi-nand0
mtd write spi-nand0 0x46000000 0 0x8000000
```

Notes:

* `mtd read/write/erase` skips factory bad blocks and prints
  `Skipping bad block at 0x...`. This build keeps the data aligned with the
  flash offset across the skip (upstream U-Boot silently shifted everything
  after a bad block by one erase block — fixed in `cmd/mtd.c` here).
* A wrong argument order (`size` passed as the 3rd/offset argument, e.g.
  `mtd write spi-nand0 0x46000000 0x8000000`) starts an offset at the end of
  the chip; this build now fails fast with
  `No good erase block found at or after ...` instead of hanging (also a
  `cmd/mtd.c` fix).
* ECC is regenerated on write; the original OOB/BMT bookkeeping is not
  restored (MediaTek BMT re-syncs at boot).
* The dump has 3 uncorrectable sectors (see `ecc-report.txt`), all inside
  Image1/Image2 — a few bytes of the stock system image cannot be recovered;
  the unit should still boot. Config/Factory/bootloader areas are clean.
* Restoring `bl2`/`fip` reverts the router to the stock LK bootloader — the
  custom U-Boot must then be re-flashed (Step 2) if wanted again.

## Security

`Config.bin`/`Factory.bin` in `stock/` may contain device credentials and MAC
data — keep this repository private, and revoke any credentials that were
ever pasted into chat logs.
